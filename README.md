# pokemon-champions-rl

Reinforcement learning system for **Pokémon Champions — Regulation M-A** (VGC doubles, 2026). The goal is to discover the strongest competitive teams for the current meta and track how they evolve over time.

The system runs end-to-end: it scrapes meta usage data, learns which team compositions perform best, trains an in-battle PPO policy, and continuously evolves team builds using a genetic algorithm and a self-play league.

---

## Format

| Rule | Detail |
|---|---|
| Format | `gen9championsvgc2026regma` — doubles, bring 4 of 6, lead 2 |
| Stat system | SP replaces EVs/IVs — 66 SP per Pokémon, max 32 per stat |
| Nature system | Stat Alignment — same +10%/−10% mechanic as natures |
| Mega Evolution | One Mega per battle, immediate on selection |
| Legendaries | Banned — no Restricted, no Paradox, no Mythicals |
| Team sheet | Open Team Sheet — opponent species are always known |

## How It Works — The 6-Stage Pipeline

```
Stage 1  →  Stage 2  →  Stage 3  →  Stage 4  →  Stage 5  →  Stage 6
Scrape      Encode       Train PPO   Analytics   Evolve       League
meta data   team obs     policy      log parser  teams (GA)   PBT self-play
```

### Stage 1 — Meta Data Collection (`src/stage1_scraper/`)
Scrapes Pikalytics for current usage rates across the Reg M-A metagame. Outputs JSON files consumed by downstream stages. Run once per meta shift.

### Stage 2 — Team & Lead Selection (`src/stage2_selection/`)
Given your 6-mon roster and the opponent's 6 species, scores all 90 valid (bring-4, lead-2) combinations and returns the best one. Trained on heuristic battle data generated by an experiment runner that exhaustively tests every combination across diverse matchups.

The bring and lead decisions are made **jointly** — a mon that scores mediocrely for bring alone may be essential to your best lead pair. Sequential models miss this; a joint scorer captures it.

### Stage 3 — In-Battle Decisions (`src/stage3_battle_decisions/`)
MaskablePPO agent that chooses moves and switches turn-by-turn. The 4,104-dim observation is sliced into per-mon blocks by `BattleStateEncoder`, which produces a 288-dim dual-slot context vector as input to the policy network.

Action space: `MultiDiscrete([107, 107])` — one action per active slot.

### Stage 4 — Analytics (`src/stage3_battle_decisions/analytics/`)
Parses battle logs into structured records. Scores per-Pokémon performance (damage contribution, KOs, survival), identifies underperformers, and flags threat Pokémon. Used as an auxiliary fitness signal alongside win rate.

### Stage 5 — Team Evolution (`src/stage4_team_evolution/`)
DEAP-based genetic algorithm over Showdown team strings. Mutation operators respect all format constraints (SP cap, Item Clause, one Mega). Fitness is the meta-weighted win rate of a frozen PPO policy against 8 archetype opponents:

| Archetype | Weight |
|---|---|
| CYBERTRON Sun | 74.5 |
| YUZU Perish Trap | 72.1 |
| KURO Rain | 67.7 |
| HYUNGWOO Sun | 65.3 |
| WOLFE Sand | 63.9 |
| WDMICHAEL TR Golurk | 61.2 |
| ROD Snow/TR | 58.8 |
| JORGE CharX/Mega Ttar | 57.4 |

**Critical design point:** `train` updates the policy. `mutate` uses a frozen policy to evaluate team quality only. Never conflate the two — fitness differences must be attributable to the team, not the policy.

### Stage 6 — PBT League (`src/stage3_battle_decisions/league/`)
Population-Based Training with 8 agents, each maintaining their own team. Each generation: all agents train → evaluate fitness → bottom agent copies weights from the top agent (exploit) → mutates its own team (explore). Every team change is logged to `evolution_log.jsonl` for full lineage tracking.

## Quick Start

```bash
# Start Showdown server + trainer container
docker-compose up

# Run a short PPO training pass
docker-compose run --rm trainer python src/train.py train --steps 10000

# Evaluate the current checkpoint against all 8 archetypes
docker-compose run --rm trainer python src/train.py evaluate --battles 20

# Evolve the team using a frozen policy (no gradient updates)
docker-compose run --rm trainer python src/train.py mutate --rounds 10

# Run the full PBT league (8 agents, 10 generations)
docker-compose run --rm trainer python src/train.py league --agents 8 --generations 10

# Scrape current meta usage data
docker-compose run --rm scraper

# Open TensorBoard (http://localhost:6006)
docker-compose up tensorboard
```

## Team Selection Commands

```bash
# Run the bring/lead experiment (generates training data)
docker-compose run --rm trainer python src/stage2_selection/experiment.py --battles 5

# Train SelectionMLP on experiment results

docker-compose run --rm trainer python src/stage2_selection/sample_scripts/recommend.py \
```

## Train vs. Mutate — Key Distinction

```
train   →  policy improves, team stays fixed
mutate  →  team evolves,    policy stays frozen
```

The intended loop:

1. **`train`** — run PPO to improve in-battle decision-making with the current team
2. **`mutate`** — use the frozen policy as a fitness oracle to find a better team composition
3. **`train`** — adapt the policy to the new team
4. Repeat

This separation means win-rate differences in `mutate` are attributable to team quality alone, not policy quality. The evolution history is recorded to `model_outputs/checkpoints/evolution_log.jsonl` on every accepted or rejected mutation.

---

## Team Evolution Tracking

Every team change — whether from `mutate` or a league exploit/explore step — is appended to `evolution_log.jsonl`:

```json
{
  "ts":             "2026-05-29T14:23:01",
  "event":          "mutation_accepted",
  "generation":     3,
  "fitness_before": 0.512,
  "fitness_after":  0.547,
  "team_before":    "...",
  "team_after":     "..."
}
```

This gives full lineage tracking of every team that was tried, accepted, or rejected — answering "how did we get here?" at any point.

## Observation Space

EncoderV2 produces a **4,104-dim** observation vector:

| Block | Count | Dim each | Total |
|---|---|---|---|
| Your active Pokémon | 2 | 418 | 836 |
| Your bench Pokémon | 2 | 393 | 786 |
| Opponent active | 2 | 400 | 800 |
| Opponent bench | 4 | 381 | 1,524 |
| Field state | 1 | 38 | 38 |
| Battle context | 1 | 120 | 120 |
| **Total** | | | **4,104** |

`BattleStateEncoder` slices this into per-mon blocks, encodes each with a shared MLP (32-dim per mon), then builds two slot-perspective context vectors (each slot sees its own mon first) → **288-dim** output to the PPO policy.
